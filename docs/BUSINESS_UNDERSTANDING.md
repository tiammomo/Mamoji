# Mamoji 业务理解

> 本文基于清理前的当前项目代码、接口、前端页面与既有文档抽取，记录 Mamoji 的旧版个人/家庭记账实现基线。项目后续定位已经调整为企业经营记账与人员经营管理系统，新的目标方向以 [ENTERPRISE_PRODUCT_POSITIONING.md](ENTERPRISE_PRODUCT_POSITIONING.md) 为准。

## 0. 定位调整说明

Mamoji 后续不再以个人或家庭记账作为产品目标。新的目标用户是初创公司团队，核心场景包括员工入职、离职、人员档案、权限管理、企业成本支出、收入、税费、预算、现金流和公司经营状态管理。

本文以下内容保留为当前代码和过渡模型说明，可用于判断哪些能力能复用、哪些领域模型需要重构。

## 1. 一句话定位

旧版 Mamoji 是一个面向个人与家庭的记账、预算管理和收支分析系统。企业版改造后，它应演进为初创公司轻量经营管理系统，统一覆盖人员、收入、成本、税费、预算、现金流和经营风险。

## 2. 目标用户与核心价值

### 目标用户

- 个人用户：记录收入/支出、管理账户余额、查看月度/年度财务概览、跟踪预算执行。
- 家庭用户：通过共享账本与成员角色管理家庭收支，理解家庭整体消费结构。
- 管理员用户：维护系统用户、角色和权限，辅助演示、运营或家庭内部账号管理。

### 核心价值

- 快速记账：支持收入、支出、退款流水，按日期、分类、类型筛选。
- 预算反馈：预算与支出联动，实时计算已用、剩余、使用率和风险等级。
- 财务洞察：提供月度概览、趋势、分类占比、年度报表、资产负债、同比环比和异常洞察。
- 家庭协作：通过账本和成员角色承载共享记账场景。

## 3. 角色、权限与访问边界

### 用户角色

- 管理员：角色值为 `1`，可进入用户管理，具备用户、账户、分类、预算管理能力。
- 普通用户：角色值为 `2`，默认无管理权限，可使用自身数据相关的核心功能。

### 权限位

系统使用整数位掩码表达权限：

- `1`：用户管理
- `2`：账户管理
- `4`：分类管理
- `8`：预算管理

账户、分类、预算写操作会校验管理员角色或对应权限位。普通注册用户默认没有这些管理权限，管理员默认拥有全部权限。

### 账本角色

账本成员角色包括：

- `owner`：账本所有者，拥有最高权限。
- `admin`：可添加成员。
- `editor`：预留编辑角色。
- `viewer`：默认只读角色。

当前实现中，账本创建人会自动成为 `owner`；添加和移除成员都只能由账本所有者执行，且不能移除所有者。可添加的目标用户必须先是同公司的有效成员，`owner` 角色不能通过成员接口授予。

## 4. 核心业务对象

### 用户

用户是认证和数据归属的基础对象，包含邮箱、密码哈希、昵称、头像、家庭 ID、角色、权限、创建/更新时间。系统以 JWT 做无状态鉴权，注册和登录开放，其余 API 默认需要登录。

头像在前端被编码为 `emoji|color` 的形式，用于设置页和侧边栏展示。

### 账户

账户表示资金容器和余额快照，类型包括：

- 现金 `cash`
- 银行卡 `bank`
- 信用卡 `credit`
- 数字钱包 `digital`
- 投资 `investment`
- 负债 `debt`

账户包含名称、类型、子类型、银行、余额、可用余额、信用额度、冻结金额、是否计入净资产、用户 ID、公司 ID、账本 ID、状态和对账日期。账户汇总输出总资产、总负债和净资产，用于账户页、高级报表资产负债视图。

旧版账户余额更接近手工维护的快照。当前企业改造后的流水创建、修改、退款和删除已在同一数据库事务中同步账户余额，并由会计经营集成测试覆盖回滚与并发场景。PostgreSQL 是账户唯一在线事实来源，不再维护账户进程 Map 或事务后双写；V18 使用强类型金额、日期、布尔和时间戳，并以外键和检查约束保护公司/用户归属、公司内账本引用及账户状态。账户创建以完整单次 INSERT 落库，并发版本从 `0` 开始。

### 分类

分类为收入/支出提供统一语义，字段包括公司 ID、用户 ID、名称、类型、图标、颜色、状态和生命周期时间。分类在公司租户内继续按用户隔离，不使用旧 `familyId` 或“系统分类”标记作为授权、更新或删除依据。

公司开通事务会为公司所有者创建通用默认分类；生产启动不再扫描已有公司补种：

- 收入：经营收入
- 支出：经营支出

演示模式会为首个公司主体补充：

- 主营业务收入、团队餐饮、差旅交通、办公采购、客户退款、离职补偿、办公租赁、税费。

名称、图标和颜色会规范化校验，同一用户在同一公司内不能创建同类型同名分类。分类一旦被流水或预算引用就不能删除，也不能改变收入/支出类型；创建、更新和删除成功后均写审计日志与 Outbox 事件。PostgreSQL 是分类的唯一在线事实来源，V20 通过公司成员复合外键、唯一约束、检查约束和触发器保护这些规则。

### 公司主体

公司主体是所有企业数据的租户根，包含主体类型、所有者、统一信用代码、币种、注册与经营地区、纳税人类型、政策画像和财年起始月。创建主体时会在同一事务中建立所有者成员关系、默认账本、默认分类、审计日志和 Outbox 事件；更新使用版本号防止并发覆盖。

PostgreSQL 是公司资料的唯一在线事实来源。V25 将生命周期时间改为 `TIMESTAMPTZ`，并以所有者外键、规范化信用代码唯一索引、主体类型/币种/地区/财年检查约束和所有者不可变触发器保护租户根；V28 一次性补齐历史公司的所有者成员、经营账本和缺失的通用分类。访问控制和各业务模块只通过 `CompanyRepository` 读取公司，不再依赖旧 Store 的公司 Map 或写入口。

### 主体间资金划转

主体划转记录公司与公司、公司与家庭主体之间的垫资、归还、费用代垫和报销付款。每条记录明确资金来源主体、目标主体、业务类型、金额、币种、发生日期、操作者和备注；操作者必须同时有权访问两端主体，同一主体不能向自身划转。记录创建后只追加、不改写，纠错应通过后续业务记录和审计流程留痕。

V26 将划转金额、日期和生命周期时间改为 `NUMERIC(20,4)`、`DATE` 与 `TIMESTAMPTZ`，并以双边主体外键、操作者外键、正金额、三位币种、合法划转类型和禁止更新或删除的触发器保护历史。`EntityTransferRepository` 在 SQL 中完成可访问主体过滤，旧 Store 不再持有划转 Map、全表投影或写入口。

### 部门

部门是 People Core 的公司内组织单元，包含名称、成本中心、部门预算、启停状态和负责人。负责人必须是同公司的员工；员工档案和公司成员的部门引用同样必须指向本公司部门，不能用跨公司 ID 绕过租户边界。同一公司内的部门名称按大小写归一后唯一。

部门创建和更新只允许公司级人事管理员执行，并与审计日志及 `people.department.<action>` Outbox 事件在同一事务提交。PostgreSQL 是部门的唯一在线事实来源；V22 将预算和生命周期时间改为 `NUMERIC(20,2)` 与 `TIMESTAMPTZ`，以复合外键、检查约束、唯一索引和公司归属不可变触发器保护组织关系。员工或部门被删除时只清空对应关系字段，不改变仍存记录的公司归属。

### 员工

员工档案是 People Core 的公司内人员主数据，覆盖账号绑定、部门与直属经理、在职状态、合同和教育资料、薪酬及五险一金测算。员工邮箱和工号在同一公司内按大小写归一后唯一，一个用户在同一公司内最多绑定一份员工档案；直属经理必须属于同一公司且不能指向本人。

创建和更新员工后，公司成员权限、任职事件、审计日志与 Outbox 事件在同一事务内同步。PostgreSQL 是员工和任职历史的唯一在线事实来源；V23 将员工薪酬、日期和生命周期字段改为 `NUMERIC(20,4)`、`DATE` 与 `TIMESTAMPTZ`，并通过外键、检查约束、唯一索引和公司归属不可变触发器阻止跨租户关系与非法状态。V24 将入职、离职和状态变更事件收口为不可更新的追加式历史，以公司内员工复合外键和操作者外键阻止跨租户或无来源事件。薪酬测算集中在 People Core 策略中，工资批次保存独立快照，历史月结不会因员工档案后续修改而漂移。

### 税务事项

税务事项记录公司在一个月、季度、年度或单次日期内的税种、计税金额、应缴/已缴金额、截止日、申报状态、缴款状态、责任人和政策口径。当前支持增值税、企业所得税、个人所得税、附加税费和印花税；它是内部待办与风险跟踪，不替代法定申报系统。

缴款状态、默认申报状态、税率和风险等级由领域规则根据金额与截止日派生；已缴金额不能超过应缴金额，同一公司同一税种和期间只能存在一条事项。零税额事项的缴款状态视为完成，但仍保留申报准备流程，不会因零金额自动标记为已申报。创建、更新和删除与审计日志及 `enterprise.tax_item.<action>` Outbox 事件在同一事务提交。

PostgreSQL 是税务事项的唯一在线事实来源。V21 将金额、税率、日期和时间戳改为强类型，并用公司外键、唯一约束、检查约束及公司归属不可变触发器保护数据；演示税务种子只在首个公司没有事项且没有税务生命周期审计时写入，用户删除后不会在重启时恢复。

### 账本

账本表示一组记账数据的协作范围，包含公司、名称、描述、币种、所有者、是否默认、状态。成员关系由 `ledger_members` 维护，并显式携带公司范围。

旧版业务上它用于家庭/多人共享账本。当前企业版将公司作为首要租户边界，账本作为公司内会计协作维度参与账户、预算与流水关联。Finance JDBC 仓储是账本和成员的唯一在线事实来源；V19 通过复合外键保证所有者和成员属于同一公司，通过部分唯一索引保证每公司最多一个默认账本，并通过数据库触发约束保护 owner 成员。并发创建经营工作区会收敛到同一默认账本，拥有财务权限且已加入账本的公司成员可以在该账本下完成账户和流水操作。

### 交易

交易是系统核心流水，类型约定：

- `1`：收入
- `2`：支出
- `3`：退款

关键字段包括公司 ID、用户 ID、账本 ID、类型、金额、分类、账户、日期、备注、原始交易 ID、已退款金额、是否可退款、命中预算 ID、幂等键和并发版本。PostgreSQL 是唯一在线事实来源，不再维护进程内流水 Map 或事务后双写。

V17 将金额、日期、退款标记和生命周期时间收紧为 `NUMERIC(18,4)`、`DATE`、`BOOLEAN` 与 `TIMESTAMPTZ`，并使用复合外键保证账户、分类、账本、预算和原流水不能跨公司引用；升级预检发现未归属、孤立或非法退款数据时会整体回滚。

交易写入规则：

- 金额必须大于 0，整数部分最多 14 位；新增收入/支出最多两位小数，更新和退款最多四位小数。
- 日期使用 ISO `yyyy-MM-dd` 格式。
- 备注最长 2,000 字符。
- 分类必须存在，并且分类类型必须与交易类型一致。
- 新增/更新支出时会尝试匹配当前有效预算，优先匹配分类预算，再匹配总预算。
- 退款交易不可编辑；可通过删除退款流水撤销退款，已经有退款历史的原始支出不可直接删除。

### 退款

退款是支出的反向调整，但以独立交易类型 `3` 保存，保留审计链路：

- 只能对支出发起退款。
- 退款金额必须大于 0，且不能超过剩余可退款金额。
- 退款日期不能早于原始交易日期。
- 原始交易累计 `refundedAmount`。
- 退款交易记录 `originalTransactionId`。
- 预算消耗计算采用有效支出，即支出减去已退款金额，避免预算使用被高估。

### 预算

预算用于期间内支出控制，支持总预算和分类预算：

- `categoryId` 为空：总预算。
- `categoryId` 非空：指定分类预算。

预算字段包括公司、名称、金额、开始日期、结束日期、预警阈值、状态、已用/占用金额、用户 ID、账本 ID、分类 ID 和并发版本。

状态约定：

- `0`：停用/取消
- `1`：进行中
- `2`：已完成
- `3`：超支

预算规则：

- 名称不能为空，最长 64 字符。
- 金额必须大于 0，且数据库按两位小数保存。
- 起始日期不能晚于结束日期。
- 预警阈值必须在 0 到 100 之间。
- 用户、账本和费用分类必须属于预算公司；过期版本更新会返回冲突，不覆盖其他请求。
- 同一用户、同一分类维度、重叠周期内不能有多个有效预算。
- 支出新增、更新、退款、删除后会刷新受影响预算的已用金额和状态。

预算派生字段：

- `spent`：已用金额。
- `remainingAmount`：剩余金额。
- `usageRate`：使用率。
- `warningReached`：是否达到预警阈值。
- `riskLevel`：`low`、`medium`、`high`、`critical`。
- `riskMessage`：面向前端的可读说明。

## 5. 关键业务流程

### 注册与登录

1. 用户提交邮箱、密码、昵称。
2. 系统检查邮箱唯一性。
3. 密码使用 BCrypt 哈希保存。
4. 登录成功后签发 JWT。
5. 前端保存 token 和用户信息，后续请求带 `Authorization: Bearer <token>`。
6. 后端过滤器解析 token，恢复当前用户上下文。

开发环境曾内置测试账号：

- 邮箱：`test@mamoji.com`
- 密码：`123456`

### 首页概览

首页面向快速感知财务状态：

- 本月收入
- 本月支出
- 本月结余
- 最近交易
- 快捷入口：记账、交易记录、报表、预算

### 记账

1. 前端选择收入/支出、金额、分类、账户、日期、备注。
2. 后端校验类型、金额、日期、分类。
3. 如果是支出，按分类预算优先、总预算兜底的顺序匹配有效预算。
4. 保存交易。
5. 刷新相关预算快照。
6. 返回交易数据和结构化风险评估。

### 退款

1. 前端从可退款支出中选择一笔交易。
2. 用户填写退款金额和退款日期。
3. 后端校验原交易类型、剩余可退金额、退款日期。
4. 更新原交易累计退款金额。
5. 创建退款交易。
6. 刷新预算快照。
7. 返回退款结果和原交易风险状态。

### 预算管理

1. 用户创建预算，设置周期、金额、预警阈值和可选分类。
2. 系统防止同分类同周期预算重叠。
3. 交易写入后预算自动重算已用金额。
4. 前端以进度条、状态标签和预警图标展示预算风险。

### 报表分析

报表从交易、分类、账户、预算聚合数据，帮助用户理解：

- 某段时间收入、支出和结余。
- 收支趋势。
- 收入/支出分类占比。
- 年度每月收支变化。
- 净资产、总资产、总负债。
- 同比和环比变化。
- 最近收支、大额收支、异常分类、预算告警。

## 6. 风控口径

交易风险分为 `low`、`medium`、`high`、`critical`。主要规则：

- 单笔大额支出：支出达到 3,000 记为 `large_expense`，风险升到 `high`。
- 单笔严重支出：支出达到 10,000 记为 `critical_expense`，风险升到 `critical`。
- 无收入支出：当月收入为 0 但已有支出，记为 `expense_without_income`。
- 收支失衡：当月有效支出 / 当月收入达到 1.20，记为 `expense_income_ratio_high`。
- 高频支出：单日支出笔数达到 12，记为 `high_frequency_expense`。
- 疑似重复：同日同分类同金额存在其他支出，记为 `possible_duplicate_expense`。
- 分类突增：同分类本月支出较上月达到 2 倍且增量达到 1,000，记为 `category_expense_spike`。
- 新分类大额：没有上月历史时，当前分类支出达到 3,000 可视为突增。
- 预算观察：预算使用率接近预警阈值前 10 个百分点，记为 `budget_watch`。
- 预算预警：预算使用率达到预警阈值，记为 `budget_warning`。
- 预算超支：预算使用率达到或超过 100%，记为 `budget_overrun`。

风险输出包含：

- 风险等级
- 命中标记
- 风险消息
- 月收入/月有效支出
- 支出收入比
- 单日支出数
- 重复交易数
- 分类本月/上月金额
- 预算额度、已用、剩余、使用率、预警阈值和状态

## 7. 前端功能地图

主导航暴露的主要页面：

- 首页：本月概览、最近交易、快捷入口。
- 新增记账：独立记账入口。
- 交易记录：支出/退款与收入双栏展示，搜索、日期筛选、分页、记账、编辑、退款。
- 统计报表：概览、年度报告、资产负债、异常洞察集中在同一报表工作台中。
- 账户管理：账户列表、账户搜索、账户新增、删除、总资产/总负债/净资产。
- 预算管理：预算列表、日期筛选、搜索、新增、编辑、删除、进度与预警。
- 设置：个人信息、密码、主题、语言，以及低频的数据与管理入口。

设置内保留的低频入口：

- 数据备份：数据量统计、导出、导入文件校验。

## 8. 后端接口地图

主要接口模块：

- `/api/v1/auth`：注册、登录、当前用户、资料更新、密码修改。
- `/api/v1/accounts`：账户 CRUD、账户汇总。
- `/api/v1/categories`：分类列表、分类 CRUD。
- `/api/v1/budgets`：预算 CRUD、生效预算、日期范围查询。
- `/api/v1/transactions`：交易列表、新增、更新、删除、可退款列表、退款。
- `/api/v1/ledgers`：公司内可访问账本列表、创建、详情、默认账本、成员列表、添加成员和移除成员。
- `/api/v1/stats`：概览、趋势、分类、年度、资产负债、同比环比、高级洞察。
- `/api/v1/backup`：数据量状态、JSON 导出、导入文件格式校验。
- `/api/v1/recurring`：基于 PostgreSQL 的周期事项 CRUD、启停和带行锁的手动入账。
- `/api/v1/admin/users`：管理员用户管理。

## 9. 数据与归属关系

核心表和实体：

- `users`
- `accounts`
- `categories`
- `transactions`
- `budgets`
- `ledgers`
- `ledger_members`

数据归属现状：

- 流水、账户、分类和预算以 `companyId` 作为租户边界，并在个人数据范围内继续带 `userId` 谓词。
- 流水引用的账户、分类、账本、预算和原流水由数据库约束保证属于同一公司。
- 账户引用的账本由数据库复合外键保证属于同一公司，账户所属用户和公司不得为空或孤立。
- 账本所有者和成员必须是同公司的有效成员；每公司最多一个默认账本，owner 成员不可删除或降级。
- 分类所属用户必须是对应公司的成员，分类公司与用户不可在创建后迁移；已被流水或预算引用的分类不能改变收支类型。
- 用户保留 `familyId`，用于兼容旧字段；新企业业务不以它作为授权边界。
- 工作台和企业读模型按访问上下文应用公司、部门或本人范围，报表不依赖进程内对象集合。

## 10. 备份与数据导入

备份状态统计：

- 用户数
- 账户数
- 分类数
- 交易数
- 预算数
- 账本数

导出与恢复能力：

- 管理员可导出带校验和的全量结构化业务数据 JSON；当前格式为 `2.2`。
- 恢复支持预检、显式 `RESTORE` 确认、单事务覆盖写入、序列校准和现有会话撤销。
- 兼容 `2.1` 与 `2.0`：旧账本成员的公司范围从账本派生，`2.0` 公司成员关系从公司负责人和员工档案重建；无法安全补全的无公司账本或无公司分类会拒绝恢复。
- 附件对象字节不包含在结构化 JSON 中，生产恢复必须配套 PostgreSQL 与 MinIO 归档。

## 11. 定期记账与收据能力现状

### 定期记账

支持周期：

- 每天
- 每周
- 每月
- 每年

记录字段：

- 名称、类型、金额、周期类型、间隔、周几、每月几号、每年几月、开始/结束日期、上次/下次执行日期、状态、执行次数、备注。

实现现状：

- 周期规则由 PostgreSQL 专属仓储持久化，服务重启不会丢失。
- 手动执行会真正创建流水，并通过数据库行锁和执行游标阻止同日重复入账。

### 收据管理

前端已实现：

- 图片拖拽/选择上传。
- 收据列表。
- 图片预览。
- 下载和删除入口。
- 404 时提示后端收据模块未启用。

后端现状：

- 票据凭证已由 Evidence 模块提供领域模型、typed JSON 与 multipart 写命令、typed 上传结果、PostgreSQL 仓储、对象存储、审批/入账状态和去重约束；流水关联直接读取权威数据库记录。无效金额、日期、状态和越权审批字段在 API 边界拒绝，更新仍支持显式 `null` 清空，批量上传仍支持逐文件部分成功。V27 将历史派生默认值改为 Flyway 一次性回填，生产启动不再扫描或逐条改写票据。

## 12. 主要实现缺口与重建提醒

若后续重建系统，应优先处理这些业务一致性问题：

- 分类、资金账户、账本及成员、流水、预算和周期事项均已完成 PostgreSQL 单一事实源改造；后续重点是统一跨模块查询契约和客户端并发版本语义。
- 流水已完成账户余额联动、`accountId` 校验、公司复合外键和 PostgreSQL 单一事实源改造；后续重点是客户端显式版本契约与更细数据范围。
- 账本列表已同时返回自己拥有和作为成员可访问的公司内账本；后续重点是将 `admin/editor/viewer` 的细粒度账本动作矩阵继续落到应用层。
- 分类当前保留“公司 + 用户”的个人数据范围；若未来要支持公司级共享科目表，需要先定义独立的共享所有权、角色权限和历史引用迁移策略，不能直接放宽现有用户谓词。
- 周期事项已持久化到 PostgreSQL，手动执行会生成交易并以数据库行锁防止同日重复入账。
- 票据后端已实现；后续重点是生产对象存储、审批策略和会计入账联调。
- 默认开发数据和 H2/MySQL 配置口径存在差异，需要在重建时明确开发、测试、生产环境的数据源策略。
