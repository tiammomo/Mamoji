# ADR 0015：类型化票据查询并下推数据库计算

- 状态：Accepted
- 日期：2026-09-05

## 背景

票据写入与上传完成类型化后，列表入口仍接收 `Map<String, String>`。非法公司 ID、金额或分页值会被静默忽略或修正，状态值没有白名单；应用服务还会加载公司全部票据，在 JVM 内依次筛选、分页和计算 20 项汇总指标。该实现的内存、网络和响应时间随公司票据总量线性增长，列表的总数与当前页也没有数据库快照一致性。

## 决策

1. `GET /api/v1/receipts` 使用 `ReceiptQueryRequest` 绑定查询参数，通过 Bean Validation 校验公司 ID、枚举白名单、ISO 日期、金额精度/范围及分页上限；空的可选筛选仍视为未指定，以兼容现有客户端。
2. API DTO 映射为不依赖 Web 的 `ReceiptListQuery`。应用服务校验开始/结束日期和最小/最大金额的交叉边界，再解析调用者可访问的公司。
3. `ReceiptVoucherRepository.findPage` 在 PostgreSQL 中执行同一条件的 `COUNT(*)` 与 `LIMIT/OFFSET` 查询，保持原有 `issue_date DESC, id` 排序。应用层以只读 `REPEATABLE_READ` 事务保证总数和当前页来自同一快照。
4. 标题、凭证号、往来方与备注继续执行不区分大小写的包含搜索；`%`、`_` 和转义符按普通字符处理，避免 SQL LIKE 元字符扩大匹配范围。
5. `GET /api/v1/receipts/summary` 返回 typed `ReceiptSummary`。金额与工作流计数通过单条条件聚合 SQL 计算，空公司稳定返回全零结构，对外 JSON 字段名保持不变。

## 影响

- 列表内存占用从公司全部票据降为最多 200 条当前页对象，筛选和分页不再依赖 JVM 全量扫描。
- 非法查询在访问仓储前返回字段级 HTTP 400；反向日期区间和反向金额区间也被明确拒绝。
- 前端 `ReceiptQuery` 使用状态联合类型，与后端允许值保持一致；既有 URL、分页 JSON 和汇总 JSON 无需调整。
- 本批发布时票据金额与日期仍是历史文本列，因此先通过已验证的规范值完成数值比较和聚合，不捆绑 schema 修改。后续 V31 类型、约束和索引硬化见 [ADR 0016：硬化票据凭证类型、租户关系与发布边界](0016-harden-receipt-voucher-schema.md)。

## 验证与回退

- 真实 HTTP/PostgreSQL 集成测试覆盖全部筛选条件、LIKE 元字符、稳定分页、非法绑定、交叉边界、公司隔离、完整汇总及空公司全零结果。
- 模块边界测试固定 API DTO 到应用查询、typed 汇总返回值，并禁止列表应用入口退回参数 Map。
- 本批没有数据库迁移；回退代码提交即可，数据库数据与前端请求格式不变。
