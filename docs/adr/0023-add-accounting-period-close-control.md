# ADR 0023：增加公司级会计期间关账控制

- 状态：Accepted
- 日期：2026-09-05

## 背景

经营流水已经以 PostgreSQL 为唯一事实源，并在同一事务中联动账户余额、预算占用、审计和 Outbox，但系统此前没有“已结账月份不可再改”的业务边界。用户可以在月末完成对账和凭证核验后，继续通过人工录入、CSV 导入、编辑、删除、退款或周期事项改变历史月份，导致已出具的经营报表与账面事实漂移。

客户端校验或普通行锁不能解决关账与入账并发：一台实例可能在另一台实例宣布关账后才把历史流水提交。关账必须和所有流水写入口共享数据库串行点，同时还要防止未来新增入口绕过应用服务。

## 决策

1. V33 为每家公司建立唯一 `accounting_period_controls` 记录，以可空的月末日期 `closed_through` 表示连续关账水位。新公司由数据库触发器同步创建控制记录，历史公司在迁移中一次性补齐。
2. `AccountingPeriodService` 是查询、关账、反结账和流水可写校验的应用边界。关账只允许推进到已完成月份；反结账可向前回退或全部开放，且必须填写 5–500 字原因。
3. 只有全公司写范围的 founder、finance_admin 或全局管理员可以关账和反结账。只读成员可查看状态但不能改变水位。所有管理命令必须提交客户端读取到的非负 `version`，过期命令返回 409 `concurrent_modification`。
4. 关账/反结账和流水写入都以 `SELECT ... FOR UPDATE` 锁定同一公司控制行。先取得锁的流水必须完整提交后关账才能推进；先完成的关账会让后续历史写入返回 409 `accounting_period_closed`。
5. 应用校验覆盖人工创建、CSV 导入、周期事项执行、更新、删除和退款。更新同时检查原日期和目标日期；删除检查被删除流水日期；退款同时检查原流水和退款日期。因为退款会原位更新原流水的已退款金额，已关账原流水也不得直接退款，需受控反结账后处理。
6. PostgreSQL 在 `transactions` 上增加 INSERT/UPDATE/DELETE 触发器并锁定同一控制行，作为遗漏入口和多版本应用的第二层防线。触发器不替代应用错误契约。
7. 关账和反结账写入审计日志及 `accounting.period.close` / `accounting.period.reopen` Outbox 事件。前端财务总览展示当前水位、最新动作和反结账原因；交易表单与批量导入对关账冲突给出明确提示。
8. 应用内结构化备份升级为 `2.3` 并保留账期水位；恢复时先用公司触发器生成的开放控制行导入历史流水，再替换为备份水位。旧 `2.2`/`2.1`/`2.0` 备份缺少该数据集时按开放账期恢复。

## 影响

- 已关闭日期内的流水和对应账户、预算副作用保持不可变，月结报表拥有稳定数据边界。
- 采用连续水位而非任意重叠期间，避免小型企业场景出现区间空洞和重叠；后续若引入法定总账，可在该水位之上增加独立期间快照。
- CSV 一批中只要存在已关闭日期，整个导入事务回滚。周期事项使用实际执行日入账，因此只要执行日开放即可正常执行。
- V33 是新增表与触发器的前向迁移，不改写现有流水。升级后所有控制初始为开放；只有新版本实例全部就绪后才应执行首次关账。

## 验证与回退

- 迁移测试验证历史/新公司控制记录、typed 列、约束及公司/流水触发器。
- PostgreSQL HTTP 集成测试验证只读成员越权、DTO 校验、并发管理员版本冲突、反结账原因、审计/Outbox、全部流水写入口回滚及数据库绕过保护。
- 锁竞态测试让在途流水持有账期锁并阻塞账户写入，确认关账必须等待该事务提交后才推进水位。
- 若 V33 发布后尚未关账，旧应用可忽略新增表。若已产生关账状态，不得直接回退到不会解释关账错误的旧应用；应先在新版本中按审计流程反结账，或停止应用并恢复发布前数据库备份。
