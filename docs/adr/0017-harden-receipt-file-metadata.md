# ADR 0017：类型化并固化票据附件指纹元数据

- 状态：Accepted
- 日期：2026-09-05

## 背景

票据主体在 V31 已完成强类型与租户关系硬化，但附件去重表 `receipt_file_hashes` 仍保留早期文本 schema：SHA-256、文件名和创建时间均可写入任意文本，JDBC 端口也用多个字符串与基本类型传递一条附件登记。上传链路还会在验证 10 MB 上限前读取整个文件计算摘要，并把客户端可能携带路径的原始文件名写入票据和去重记录。

该表既决定同公司附件幂等，又参与结构化备份恢复，因此必须把摘要、元数据、时间和不可变语义统一到应用与数据库边界。

## 决策

1. 使用 `ReceiptFileDigest` 表示规范的小写 64 位 SHA-256，以 `ReceiptFileRegistration` 一次传递公司、票据、摘要、规范文件名、大小和 `OffsetDateTime`；仓储端口不再接受散落的字符串参数。
2. 上传先校验非空、10 MB 上限、客户端文件名 basename/长度/控制字符、扩展名、魔数和声明类型，再读取完整内容计算摘要、取得公司范围事务锁并检查重复。对象存储与数据库统一使用已校验的 basename。
3. Flyway V32 在改写前拒绝孤立或跨公司引用、非法摘要/文件元数据、负大小、不可解析或非有限时间，以及规范化后重复摘要。可确定的大小写、空白和客户端路径会规范化；其他脏数据使迁移原子回滚并保持 V31。
4. `sha256` 与 `file_name` 收紧为有界 `VARCHAR`，`created_at` 改为 `TIMESTAMPTZ`；数据库检查公司/票据 ID、摘要格式、basename、大小和有限时间，复用 V31 的公司票据复合外键，并禁止附件指纹记录原位修改。
5. 查询索引改为 `(company_id, voucher_id)`，与租户范围读取和复合外键一致；同公司摘要唯一索引继续承担最终去重约束。
6. 结构化备份格式保持 `2.2`，但回归测试必须证明 typed 附件记录可导出并恢复。附件对象字节仍由配套 MinIO 归档保护。

## 影响

- 无效或超限附件在读取完整内容、上传对象和创建票据前返回 HTTP 400；同公司相同内容仍稳定返回 409。
- 附件指纹成为追加后不可修改的证据元数据；删除所属票据时仍按外键级联删除该记录。
- V32 会锁定并改写附件指纹表，且旧版本字符串 JDBC 写法不兼容 typed 时间列。生产升级必须使用维护式发布和默认一致性备份，不得让 V31 应用与 V32 schema 重叠运行。

## 验证与回退

- 迁移测试覆盖 V26 历史数据到 V32 的摘要/文件名规范化、typed 列、约束、索引、不可变触发器，以及非法 V31 摘要导致完整回滚。
- 领域、JDBC 与 HTTP 测试覆盖摘要生成、typed 登记、basename、超长文件名、上传去重和时间读取；结构化备份测试覆盖附件元数据往返恢复。
- V32 是前向迁移。若迁移后应用不可用，保持应用停止，从发布前 PostgreSQL 与 MinIO 一致性备份恢复后再启动 V31 镜像；不要只回退应用镜像。
