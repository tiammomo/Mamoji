# ADR 0016：硬化票据凭证类型、租户关系与发布边界

- 状态：Accepted
- 日期：2026-09-05

## 背景

票据 API、应用命令、领域模型和查询返回值已经类型化，但 `receipt_vouchers` 仍保留早期文本 schema：金额、税率、业务日期和生命周期时间都以字符串存储，状态值、日期顺序、审批审计和公司引用主要依赖应用代码。查询适配器因此必须反复执行字符串清理与类型转换；绕过应用的错误写入可能造成跨公司关联、非法工作流状态或无法聚合的数据。

金额和时间列的类型转换会重写并锁定票据表，新 schema 也不兼容仍使用字符串参数的旧后端实例，因此该迁移不能按新旧实例重叠的滚动方式发布。

## 决策

1. Flyway V31 在任何改写前验证票据及文件哈希的公司、用户、审批人和流水引用，枚举、金额精度与范围、日期、时间戳、字段长度、幂等键及生命周期组合。任何非法历史行都会使整个事务回滚，schema 版本保持 V30。
2. 迁移先规范化可确定的大小写、首尾空白和空可选值，再把金额与税率改为 `NUMERIC`、业务日期改为 `DATE`、生命周期时间改为 `TIMESTAMPTZ`，并为描述、状态和文件元数据设置有界 `VARCHAR`。
3. 数据库增加状态、金额、日期、审批审计、入账生命周期、文件大小、幂等键和版本检查约束；公司、操作者、审批人及同公司流水使用外键保护。票据公司归属不可更新，文件哈希通过 `(company_id, voucher_id)` 复合外键阻止跨公司引用。
4. Evidence JDBC 适配器使用 `BigDecimal`、`LocalDate` 和 `OffsetDateTime` 直接绑定与读取 typed 列；汇总和筛选不再对文本执行清理或运行期转换。应用层在持久化及对象上传前拒绝税额大于金额、隐含税率超过 100% 和到期日早于开票日，避免把约束冲突暴露为 500。
5. 票据列表索引统一以 `company_id` 开头，并使用 `issue_date DESC, id` 对齐稳定分页；补充凭证类型、税期、抵扣、入账状态和缺失流水关联索引。
6. 默认生产发布先构建后端与前端镜像，再执行一致性备份，并让旧入口、前端和后端保持停止直至新版本启动。即使显式跳过备份，部署脚本也会先停止旧应用，禁止旧 JDBC 写法与 V31 schema 重叠运行。

## 影响

- PostgreSQL 成为票据基础类型、租户关系和关键生命周期规则的最终保护层，应用校验继续提供可理解的 HTTP 400。
- 既有 HTTP JSON 字段名和数值表示保持不变；数据库内部不再接受任意文本金额、日期或状态。
- V31 会取得表级锁并重写若干列。生产升级必须安排维护窗口、先在备份副本演练并使用默认一致性备份；本次升级不得设置 `SKIP_BACKUP=true`。
- 备份脚本单独运行时仍恢复先前服务状态；仅部署脚本通过内部开关让成功备份后的旧应用保持停止。备份失败时仍会尝试恢复原服务。

## 验证与回退

- PostgreSQL 迁移测试覆盖 V26 经 V27 回填到 V31、typed 列和索引、关键约束、租户外键、公司不可变，以及非法 V30 数据导致 V31 整体回滚。
- 领域、JDBC 与真实 HTTP 测试覆盖 typed 映射、已入账初始化、创建/更新边界、显式置空及既有票据工作流。
- V31 是前向迁移，不删除或改写已发布 migration。若应用在迁移后不可用，停止新版本并从发布前 PostgreSQL 与 MinIO 一致性备份恢复，再切回旧镜像；不要只回退旧镜像去访问 V31 schema。
