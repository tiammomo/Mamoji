# ADR 0022：流水更新与删除必须携带客户端版本

- 状态：Accepted
- 日期：2026-09-05

## 背景

经营流水会同步影响资金账户余额、预算占用、审计和 Outbox。`transactions` 已有非负 `version`，JDBC 更新和删除也使用版本条件，但公开 API 没有接收客户端读取到的版本。应用用例先锁定流水、再读取最新记录，因此两个旧页面请求会顺序执行；后到的编辑可能覆盖先到结果，旧列表也可能删除在读取后已经退款或调整的流水。

数据库行锁能保证单次账户和预算联动原子，却不能证明用户确认的是当前业务事实。对于具有多项下游副作用的流水，静默接受旧意图会把技术一致性问题放大为资金与预算事实错误。

## 决策

1. `PUT /api/v1/transactions/{id}` 的 JSON 必须提交非负 `version`；`DELETE /api/v1/transactions/{id}` 必须以查询参数提交非负 `version`。缺失或负值在 API 边界返回 HTTP 400。
2. 应用服务完成当前用户、公司和所有者范围判断后，将请求版本与锁定行的版本比较。过期请求返回统一 HTTP 409 `ProblemDetail`，`code` 为 `concurrent_modification`；版本不匹配时不锁账户、不调整预算，也不写审计和 Outbox。
3. JDBC 的 `WHERE id = ? AND version = ?` 更新与删除继续保留，作为应用前置条件后的第二层并发保护。成功更新递增版本，成功删除使用被确认的同一版本。
4. 退款 API 仍表示创建一条新的业务事件，不增加客户端版本参数。退款服务继续以原流水行锁和剩余可退金额约束串行处理；退款造成的原流水版本变化会使此前打开的编辑或删除意图失效。
5. 前端编辑使用详情接口返回的版本，冲突时保留弹窗并重载最新详情；列表删除使用当前行版本，冲突时取消删除并刷新列表。其他业务型 409 不得被误判为并发冲突。

## 影响

- 同一版本的并发更新最多一个成功，账户余额和预算只应用胜出者的差额；旧版本删除不会产生任何资金回滚。
- API 客户端必须先读取流水并回传版本。更新版本放在 JSON 中，删除版本放在查询参数中；不提供静默套用数据库当前版本的兼容路径。
- 无 schema 或环境配置变更，现有 `version` 列、约束、行锁与仓储乐观锁继续使用。
- 退款、导入和幂等创建的既有语义不变；它们不是对旧快照的人工更新。

## 验证与回退

- PostgreSQL HTTP 集成测试覆盖更新/删除缺失版本、同版本并发更新、旧版本删除、账户余额只调整一次、当前版本删除后余额恢复及单次更新审计。
- 前端类型检查确保更新和删除调用必须提供版本，生产构建验证编辑详情重载与列表刷新路径。
- 回退应用代码即可恢复旧契约，数据库无需回滚；回退同时恢复静默覆盖和旧列表删除风险，只应作为短时应急措施。
