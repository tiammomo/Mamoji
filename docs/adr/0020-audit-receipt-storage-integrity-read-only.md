# ADR 0020：只读盘点票据对象存储完整性

- 状态：Accepted
- 日期：2026-09-05

## 背景

事务补偿可以处理应用已知的上传回滚，却无法覆盖进程在对象写入后崩溃、历史版本缺陷、人工迁移或独立恢复造成的 PostgreSQL 与 MinIO 偏差。票据附件属于企业财务证据，既需要发现数据库有引用但对象缺失的数据损失，也不能仅因一次扫描未找到引用就自动删除对象。

生产环境支持多后端副本，还可能保留历史凭证所引用的旧 bucket。盘点必须避免各副本重复扫描、在途上传误报和无界清单占满 JVM 内存，并给运维提供低基数告警及可定位的有限样本。

## 决策

1. 增加 `receipt-storage-integrity-audit` 定时任务，复用 PostgreSQL `scheduled_job_leases`。每分钟仅检查是否到期，默认每 6 小时执行一次，租约默认 30 分钟；同一时刻只有持有当前租约的实例扫描。
2. 从 `receipt_vouchers` 读取全部 provider 为 `minio` 的持久化引用，并扫描当前配置 bucket 及引用中出现的历史 bucket。MinIO 只递归列举 `receipts/` 前缀，不读取对象内容，也不执行删除或改写。
3. 将引用与对象按 `(bucket, objectKey)` 对账，分别记录缺失对象、无引用对象、非法引用和重复引用。无引用对象只有在最后修改时间早于默认 1 小时宽限边界时才成为孤立候选；更年轻的对象单独计数并延后判断，避免把在途上传误报为孤立对象。
4. 数据库引用和对象清单共用默认 100,000 条硬上限，允许配置到最多 1,000,000。任何一侧超限或扫描异常均令本次任务失败，不使用截断数据生成“干净”结论。
5. 指标只使用固定的 `outcome` 和 `type` 标签。完整对象键只出现在排序后、默认最多 10 条的日志样本中。缺失对象触发 critical 告警，其余不一致和任务失败触发 warning；运维确认原因前不自动清理任何候选对象。
6. 本地默认关闭盘点；生产 Compose 默认启用，环境预检和应用启动 guard 均要求 `MAMOJI_RECEIPT_STORAGE_AUDIT_ENABLED=true`。

## 影响

- PostgreSQL 与当前/历史 MinIO bucket 的结构性偏差会在最多一个盘点周期内进入指标与日志，且多副本不会共同放大扫描负载。
- 扫描内存受硬上限约束；对象量超过上限会持续告警，运维必须先扩容上限或设计分页/外部清单方案，不能把失败当作无异常。
- 年龄宽限降低在途上传误报，但不能证明孤立候选可以删除。备份、恢复、保留期、法律冻结及人工审批仍是清理前置条件。
- 本批不修改 schema，不提供删除 API，也不改变票据下载和写入路径。

## 验证与回退

- 领域测试覆盖匹配、缺失、孤立候选、年轻对象、重复引用、样本上限、重复对象及字节溢出。
- 应用与 MinIO 适配测试覆盖历史 bucket、分布式租约、固定标签指标、关闭开关、扫描失败和硬上限拒绝；生产脚本、Compose 与 Prometheus 规则纳入全量门禁。
- 回退代码和盘点配置即可停止新扫描；计数器历史和审计日志应保留用于后续人工对账。
