# ADR 0021：票据更新必须携带客户端版本

- 状态：Accepted
- 日期：2026-09-05

## 背景

`receipt_vouchers` 已有非负 `version`，JDBC 更新也使用 `WHERE id = ? AND version = ?` 防止同一服务事务中的并发覆盖。但公开更新用例会先以 `SELECT ... FOR UPDATE` 读取最新记录，再用该最新版本保存；客户端没有提交它实际读取到的版本。两个浏览器基于同一份旧票据编辑时，第二个请求会在等待行锁后读取第一笔更新的结果并继续写入，旧页面因此可能无提示地覆盖新数据。

票据同时承载金额、税务、报销与会计状态。仅依赖数据库行锁可以保证单条 SQL 完整，却不能表达用户是否接受在自己读取后发生的业务变化。

## 决策

1. `PUT /api/v1/receipts/{id}` 必须提交非负 `version`，表示客户端读取该票据时得到的版本；缺失或负值在 API 边界返回 HTTP 400。
2. 应用服务先完成用户、公司与财务写权限判断，再将请求版本与锁定行的当前版本比较。这样过期请求返回统一 HTTP 409 `ProblemDetail`，`code` 为 `concurrent_modification`，同时不向无权用户泄露当前版本。
3. 版本匹配后才允许修改领域对象、写审计或发布 Outbox 事件。JDBC 的带版本更新继续保留，作为应用校验后的第二层并发保护。
4. 审批模块调用的内部 `ReceiptApprovalStatusService` 不增加客户端版本参数。该路径由服务端工作流驱动并以行锁串行状态迁移；工作流造成的版本递增会使此前打开的人工编辑页面在保存时收到 409。
5. 前端所有票据更新都提交列表响应中的版本。收到 `concurrent_modification` 时关闭旧编辑表单或中止快捷动作、重新加载列表，并要求用户基于最新数据重新确认；其他 409 仍保留各自业务错误语义。

## 影响

- 同一版本的两个并发更新最多一个成功，另一个明确冲突；旧请求不能产生审计、Outbox 或额外版本递增。
- 直接调用更新 API 的客户端必须先读取票据并回传 `version`。这是有意的契约收紧，不提供缺失版本时静默套用当前版本的兼容行为。
- 无 schema 迁移；现有 `version` 列、非负约束和 JDBC 乐观锁继续使用。
- `PUT` 仍保留既有部分更新与显式 `null` 清空语义，`version` 仅是写入前置条件，不是可修改业务字段。

## 验证与回退

- HTTP 集成测试覆盖缺失版本、合法版本、旧版本重放以及两个并发写入者；并断言冲突请求不产生第二条更新审计。
- 前端类型检查确保每条更新路径都携带版本，页面仅按标准问题码处理并发刷新提示。
- 回退应用代码即可恢复旧契约，数据库不需要回滚；但会重新允许旧页面顺序覆盖，因此只应在紧急故障处置中短暂使用。
