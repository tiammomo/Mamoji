# ADR 0003：删除生产启动期全表兼容修复

- 状态：Accepted
- 日期：2026-09-04

## 背景

`EnterpriseDataInitializer` 曾在每次应用启动时扫描全部公司和员工，补写公司画像、薪酬派生值，并根据账号类型、职位名称和在职状态推断员工访问角色。随后 `MembershipBootstrapSynchronizer` 又扫描全部公司和员工，把员工角色写入权威 `company_memberships` 表。

这些逻辑适合早期 schema 演进阶段，但不适合作为生产启动行为：启动耗时和写放大会随租户数据增长，职位名称推断还会覆盖管理员已经明确配置的授权。公司历史默认值已由 V25 一次性补全并受约束保护；员工字段已由 V23 强类型化，薪酬派生规则则在员工仓储读写边界统一执行；`company_memberships` 自 V8 起就是账号与公司的授权事实来源。

## 决策

1. 删除 `EnterpriseDataInitializer` 中公司画像、员工薪酬和访问角色的启动期全表修复。生产 `bootstrap` 模式检测到已有公司后，不再扫描或改写公司、员工和成员数据。
2. 删除 `MembershipBootstrapSynchronizer`。不得在应用重启时从可选员工档案反向覆盖权威成员授权，也不得再根据职位名称猜测角色。
3. 首次初始化创建公司后立即调用 `CompanyMembershipRepository.ensureOwner`，创建带账号的员工后立即调用 `CompanyMembershipRepository.synchronize`。首次数据与其授权关系在同一编排边界显式产生。
4. 保留员工仓储边界的 `EmployeeCompensationPolicy.hydrate`：它负责当前薪酬政策投影，不再借应用启动将投影批量持久化。
5. 本地 `demo` 模式暂时保留家庭主体、薪酬样例和主体划转夹具；它们不进入生产 `bootstrap` 路径，后续再迁到显式开发 profile 或独立任务。

## 数据迁移

本决策不新增 Flyway migration，也不改变表结构或 HTTP 契约。V23 和 V25 已完成可确定的历史员工/公司数据规范化，V8 已从当时的公司负责人和员工档案建立成员关系。在线公司和员工写用例也一直同步维护 `company_memberships`。

不新增“最后一次同步”迁移是有意为之：`company_memberships` 是当前授权事实，使用员工职位或员工角色覆盖它会把旧的推断规则重新施加到人工配置上。升级前无需数据改写；如运维审计发现成员关系缺失，应依据真实授权记录显式修复，而不是从职位名称推断。

## 影响

- 已有企业数据经过 `EnterpriseDataInitializer` 时不再产生与公司、员工或成员数量成比例的查询和更新。
- 重启不会再改变人工配置的成员角色；管理员账号和公司所有者仍由访问控制的显式规则识别。
- 首次生产初始化及本地 demo 初始化仍会得到公司所有者和带账号员工的成员关系。
- 启动进程中仍存在首次数据和 demo 夹具编排，因此本决策本身不解除单实例保护。

## 回滚

没有 schema 变更，应用镜像可以直接回滚。回滚到旧版本会恢复启动期全表扫描，并可能再次按职位名称覆盖成员授权；执行回滚前应导出并核对 `company_memberships`，回滚后重新检查成员角色和范围。新版本创建的公司、员工和成员记录与旧版本数据格式完全兼容。
