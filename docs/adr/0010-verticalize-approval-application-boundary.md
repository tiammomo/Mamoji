# ADR 0010：纵向收口审批应用边界与业务对象引用

- 状态：Accepted
- 日期：2026-09-05

## 背景

审批 Controller 和状态机已经位于 `approval` 模块，但用例服务仍留在横向的 `com.mamoji.service` 目录，并直接依赖票据仓储与票据服务。审批申请使用 `entity_type + entity_id` 引用不同业务对象，历史实现只校验票据：交易、预算、员工和薪酬批次可以提交不存在或属于其他公司的 ID，形成无法追溯且违反租户边界的审批记录。

## 决策

1. 将审批用例迁入 `com.mamoji.approval.application.ApprovalApplicationService`，HTTP 路径、请求 DTO、响应结构和状态机保持不变。
2. 在审批应用层定义 `ApprovalEntityGateway`，应用服务只通过该契约校验引用并同步业务对象状态。
3. PostgreSQL 适配器按固定白名单处理 `receipt_voucher`、`transaction`、`budget`、`employee` 和 `payroll_run`，创建审批前同时校验对象存在且 `company_id` 等于审批公司。
4. 保留原有票据提交者或财务管理员权限校验；审批通过、驳回或撤回后仍通过适配器同步票据状态。
5. 使用模块边界测试禁止审批应用服务重新依赖票据仓储、旧票据服务或回迁到横向 Service 包。

## 影响

- 跨公司或不存在的业务对象引用统一返回 400，且不会写入审批记录。
- 审批应用层不再了解票据持久化实现，后续票据纵向迁移只需替换基础设施适配器。
- 当前审批自身的 SQL 仍由应用服务持有；后续将通过审批仓储端口迁入 `approval.infrastructure`，不在本次改动中扩大 API 或数据库变更范围。
- 本次没有数据库结构或公开 API 变更，因此无需迁移与客户端切换。

## 验证与回退

- 集成测试覆盖交易、预算、员工、薪酬批次的跨公司引用及不存在对象。
- 既有票据审批测试继续覆盖提交权限和状态同步。
- 回退只需回退应用边界提交；没有需要逆向处理的数据迁移。
