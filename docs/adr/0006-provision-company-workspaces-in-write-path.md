# ADR 0006：将公司工作区创建收口到业务事务

- 状态：Accepted
- 日期：2026-09-05

## 背景

线上创建公司已经同步建立所有者成员、默认账本和通用分类，但生产首次公司仍先写入主体，再依赖 `LedgerDataInitializer` 与 `CategoryDataInitializer` 在应用启动后扫描全部公司补种。该模型把新租户必需数据分散在三个生命周期阶段；已有公司越多，启动读放大越明显，多实例同时启动也会重复争抢相同的唯一键和 advisory lock。

账本和分类是公司可用工作区的一部分，应在主体创建事务内完成。历史公司可能来自旧版本或人工导入，仍需要一次性前向迁移保证升级后的基线完整。

## 决策

1. 新增 `CompanyProvisioningService`，在同一 Spring 事务中写入公司、所有者成员、经营账本和所有者通用收入/支出分类；生产首次公司与 HTTP 在线创建公司共用该入口。
2. 删除生产 `CategoryDataInitializer`。原共享账本初始化器改为仅在 `demo` 模式注册的 `DemoLedgerDataInitializer`，稳定 Bean 名只用于本地样例初始化顺序；`bootstrap` 上下文不存在账本或分类扫描 Bean。
3. 新增 V28 Flyway migration：规范历史公司所有者成员；仅对完全没有账本的公司创建默认账本；为选定经营账本补齐所有者成员；只补齐公司所有者缺失的收入或支出分类。已有账本和自定义分类不替换、不改名。
4. 默认账本名称受 V19 的 120 字符约束，在线创建与 V28 均按 Unicode 字符安全截断，允许公司名称使用数据库支持的最大长度。
5. 使用真实 PostgreSQL 测试覆盖空工作区补齐、已有非默认账本保留、自定义分类保留、最长公司名在线创建，以及生产 Bean 图不含扫描初始化器。

## 数据迁移

V28 不修改表结构。迁移依赖既有公司、用户、成员、账本和分类外键，在单个 Flyway 事务内执行幂等插入或受条件限制的成员更新。公司已有任意账本时不会额外创建默认账本；公司所有者已有同类型分类时不会新增通用分类。

升级前应在备份副本统计无账本公司和所有者缺失分类，并核对 V28 结果。迁移完成后，Flyway 历史记录是旧数据已完成工作区补齐的权威证据。

## 影响

- 生产应用启动不再遍历 `companies` 创建账本、成员或分类。
- 新公司在接口返回成功前已经具备可用的成员授权和会计工作区；任一步骤失败都会随外层事务回滚。
- demo 仍可在显式 demo 模式扫描并修复样例账本、补充详细样例分类，不进入生产 Spring 上下文。
- V19/V20 的唯一索引、复合外键和 advisory lock 继续保护并发创建及租户范围。

## 回滚

V28 是前向数据迁移，不删除 Flyway 历史记录回滚。发布失败时停止新版本并从迁移前备份恢复；若 V28 已成功而应用镜像需要回退，旧初始化器会看到已有账本和分类并保持幂等。发现补齐规则问题时发布新的前向 migration 修正。
