# ADR 0001：删除 EnterpriseStore 兼容层

- 状态：Accepted
- 日期：2026-09-04

## 背景

业务对象已经迁入各自模块仓储，`EnterpriseStore` 不再持有集合或承担数据访问，但仍同时转发跨模块审计并通过 `@PostConstruct` 编排首次企业数据和本地演示夹具。这个历史名称会掩盖真实职责，也让多个业务模块继续依赖一个不再是 Store 的横向组件。

## 决策

1. 删除 `EnterpriseStore`，禁止保留兼容别名。
2. 由 Platform Audit 的 `AuditTrailService` 统一构造带时间戳的 `AuditEvent`，并通过追加式 `AuditLogRepository` 写入；业务模块不直接写审计表。
3. 由 `EnterpriseDataInitializer` 单独编排首次企业数据和本地演示数据。它不暴露运行期业务查询或写命令，其他初始化器通过显式 Bean 依赖声明执行顺序。
4. 启动兼容补全只有在数据确实变化时才写回，避免每次启动产生无效更新。
5. 边界测试必须确认旧类不存在，并保护审计仓储不增加更新或删除操作。

## 数据迁移

本决策不改变表结构、既有数据或 HTTP 契约，不新增 Flyway migration。审计仍写入 `audit_logs`，启动数据仍通过现有模块仓储写入相同表，因此发布前后数据格式完全兼容。

## 影响

- 业务模块依赖清晰的审计应用边界，不再依赖历史横向 Store。
- 启动数据职责仍在应用进程内，但已经成为可识别、可单独测试和可继续迁出为 bootstrap job 的边界。
- 构造器依赖会在多个模块同步变化；完整 Spring 上下文和三组 PostgreSQL 集成套件是必需合并门禁。

## 回滚

若新应用无法启动或审计行为异常，回滚到合并前的应用镜像或代码提交即可。由于没有 schema 或数据迁移，不需要数据库降级；回滚前后共用相同的 `audit_logs` 和业务表。若仅部分实例完成发布，应停止滚动发布并统一回到同一应用版本，避免不同 Bean 初始化顺序并存。
